# Tier 1 plans: orders, lab field work and reports

**Status:** active. These are plans only; no screen code has been written for any of them.
**Rule:** `DESIGN.md` §5 and `CLAUDE.md`. Every screen below is Tier 1 on the canvas. Each
needs a named design reviewer **and** clinical or legal sign-off before its branch is opened,
and is never generated by AI without that review. Write the approvers' names and the date in
the **Approved by** line.

The backend each plan needs is being built on its own (non-Tier 1) branches:
`feat/order-payments`, `feat/rx-upload-any-format`, and the lab-order and medicine-master
tickets that follow. These plans cover only the screens and the clinical decisions.

Each plan is one ticket, one branch and one PR.

---

## 1. Report explainer (SK-047, SK-083)

**Approved by:** _(design reviewer; clinical lead / medical advisor)_

**Screens.** `ReportInsights` (mobile), `WebReportInsights`, `WebReportAssistant` ("Ayush
report explainer"), and the entry points in `MyReports` and `WebMyLabTests`.

**Today.** After a doctor reviews a lab report and releases it (`REPORT_RELEASED`), the student
sees the document and the doctor's note. There is no plain-language explanation.

**Change.**
1. The explanation is shown only for a released report, never before review, and never for a
   value the doctor has flagged critical until the doctor has acknowledged it.
2. Source of each sentence: the lab's reference range and the doctor's note. Any generated
   text is drafted from an approved template set per test, reviewed by the medical advisor,
   and labelled as general information, not a diagnosis.
3. Every screen carries "Talk to a doctor about this report" (plan 2) and the crisis/urgent
   route for out-of-range values the advisor marks urgent.
4. No explanation reaches any commerce surface (Rule L); no "buy" suggestions.

**Decisions needed from the medical advisor.** Which tests get explanations first; the wording
template per test and per range band; which values count as urgent; whether AI-drafted text
is allowed at all, and if so the review step.

**Tests.** Unreleased and critical-unacknowledged reports show nothing. Text matches the
approved template for each band. Telugu and Hindi copy reviewed by a native speaker.

## 2. "Consult about this report" prompt

**Approved by:** _(design reviewer; clinical lead)_

**Screens.** The released-report view in `MyReports` / `WebMyLabTests` and the explainer.

**Change.** After release, offer a consultation booking pre-linked to the report (the doctor
sees the report in the appointment). Booking uses the normal consultation flow and price, paid

**Tests.** Prompt only after release. The booking carries the report id; only the booked doctor

## 3. Prescription to order (pharmacy picker, price, pay)

**Approved by:** _(design reviewer; clinical lead; pharmacist adviser)_

**Screens.** The e-prescription view (`MyPrescriptionsPanel`, canvas `Prescribe` counterpart on
the student side) and `DispenseRegister`.

**Today.** The student types a raw `pharmacyId` (`MyPrescriptionsPanel.tsx:198`) to send a
prescription for dispensing. Dispenses have no price and no payment.

**Change.**
1. Replace the free-text id with a pharmacy picker (active `ServiceProvider` of kind PHARMACY,
   name and area only).
2. The pharmacy prices the dispense after its review; the student sees the price and pays
   through the payable API before the pharmacy releases the medicines.
3. Substitutions stay the prescriber's decision (existing rule). Same-salt options from the
   medicine master are shown to the pharmacist and prescriber only, never offered to the
   student as a swap.
4. The prescription content is never shown on a shop or cart surface (Rule L): the order shows
   "Prescription order #…", a price and a status.

**Tests.** No typed id accepted. Unpaid dispenses cannot move to dispatch. Price is set by the
owning pharmacy only. Nothing clinical in the payment or order payloads.

## 4. Student prescription upload screen (SK-065)

**Approved by:** _(design reviewer; clinical lead; privacy owner)_

**Screens.** `PrescriptionUpload`; the attachment view in `VendorRxReview`.

**Change.** Build the canvas screen on top of the upload API from `feat/rx-upload-any-format`:
camera or file (image, PDF and other supported formats), choose a pharmacy, send for review,
see the review status. The pharmacist opens the file through the short-lived authorised link.
The screen lives in the student's health area, never in the shop.

**Decisions needed.** Retention period for uploaded prescriptions; whether the student can
withdraw one after the pharmacist has opened it.

## 5. Lab field work: collection, cold chain and queue

**Approved by:** _(design reviewer; lab partner lead; clinical lead)_

**Screens.** `LabCollection`, `StaffCollect`, `LabColdChain`, `LabQueue`, and the home sample
pickup screen (`HomeSamplePickupScreen.tsx`, empty today).

**Today.** These screens call no API. The collector is a free-text name typed by the lab.

**Change.** Wire them to the lab-order backend (collector is a staff account of the lab;
assignment, check-in at the address, sample collected with tube count and time, handover to
the lab, temperature log). Every state the lab state machine already has
(`clinical_fulfilment.py`) is shown, including recollection.

**Decisions needed.** Which identity check the collector does at the door; what the cold-chain
log must record to be acceptable to partner labs.
