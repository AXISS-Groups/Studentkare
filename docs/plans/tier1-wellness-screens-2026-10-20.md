# Wellness screens (water, activity, weight & BMI, doses, widgets): plans awaiting review

**Status:** active. Plans only; no screen code has been written for any of them.
**Rule:** `CLAUDE.md` and `DESIGN.md` §5. Tier 1 screens need a named design reviewer **and**
clinical/legal sign-off before a branch is opened, and are never generated by AI without that
review. Screens with no canvas brief need a canvas design first. Write the approver's name and
the date in each **Approved by** line.

The backends these screens need are on `feat/wellness-logs` (migration `c3e252d528c4`, branched
from `c5f2a9d4e7b1`). Each plan below is one ticket, one branch and one PR.

**Shared rules for every plan.**
- All of this is clinical-plane data (`core/rule_l.py` `WELLNESS_STORES`): owner-only, never on a
  shop, cart, offer, receipt, upsell or campus/admin surface. Another student's id is a 404.
- No points, medals, streak rewards, levels, leaderboards or comparisons with other students.
  The APIs return none, and screens must not compute any.
- "Today" is the student's local day from `care_notification_preferences.timezone`
  (Asia/Kolkata when unset or unknown). Every response that depends on it returns `date` and
  `timezone`; screens show the server's day, not the device's.
- Every state from DESIGN.md §6, and crisis support reachable from any screen a student in
  distress could be on.

## 1. Water intake (bottle that fills, % of goal, −/+ and Add)

**Approved by:** _(design reviewer)_

**Tier.** 2 (wellness, no clinical value). **No canvas brief exists.** `CampusWater.md` is the
hostel *water-quality* radar for campus admins and is unrelated. Needs a canvas design (phone
frame) before build. Icons `bottle` and `droplet` exist in `design/icons/icon-manifest.json`;
anything else the design adds must be checked against the manifest first.

**Backend (ready).**
- `GET /api/wellness/water/today` → `{date, timezone, consumedMl, goalMl, goalSource: "DEFAULT"|"OWNER", percent, entries:[{id, amountMl, recordedAt, source}]}`. `percent` is not capped (2,400 of 2,000 = 120); the bottle caps its own fill at full.
- `POST /api/wellness/water {amountMl: 10–2000, recordedAt?}` (201) → `{id, …today}`. `recordedAt` optional, must carry a timezone, not in the future, at most 7 days old.
- `DELETE /api/wellness/water/latest` → `{removedId, …today}`; 404 "No water logged today." This is the **−** control: it removes the newest entry of today. Corrections are deletions, never negative amounts, so a total can't go below zero. An older entry is removed with `DELETE /api/health/readings/{id}`.
- `GET /api/wellness/water/goal` → `{goalMl, goalSource, minMl: 500, maxMl: 6000}`; `PUT /api/wellness/water/goal {goalMl: 500–6000}`. Default 2,000 ml, reported as `DEFAULT` until the student sets one.

**Screen must.**
1. **+** adds a fixed glass size the student chooses (the screen holds the size; the API takes ml);
   **Add** opens a custom amount. **−** calls `DELETE …/latest` and is disabled when `entries` is empty.
2. Say "default goal" when `goalSource` is `DEFAULT`; goal editing shows the 500–6,000 bounds.
3. No praise or guilt copy around the goal ("You crushed it!", "You're behind"). Reaching 100 % is
   shown as a full bottle and the number, nothing more.
4. States: loading, first use (no entries, default goal), some water, at/over goal, error, offline
   (read-only last value with its date).

**Questions for the reviewer.** Glass sizes to offer. Whether a reminder to drink is wanted at all
(it would need its own generic notification copy and a preference).

## 2. Activity trends (period picker, totals/averages, best-day card)

**Approved by:** _(design reviewer; clinical lead for the heart-rate split)_

**Brief.** `VitalTrends.md` is **Tier 1** because it shows heart rate (`illustration-sparkline-bpm`).
**Proposal: split it.** A Tier 2 *Activity* screen for steps, distance, floors, active energy and
standing minutes (and, if wanted, a water history), and VitalTrends stays Tier 1 for heart rate
and other vitals. The activity screen needs its own canvas design; VitalTrends keeps its brief.

**Backend (ready).**
- `GET /api/activity/trends?period=this_week|last_week|month|year` → `{period, timezone, from, to, daysInPeriod, metrics:{steps|distanceKm|floors|activeEnergyKcal|standingMinutes: {unit, total, dailyAverage, daysWithData}}, bestDay:{date, steps, distanceKm, floors}|null, days:[{date, steps, distanceKm, floors, activeEnergyKcal, standingMinutes}]}`.
  Weeks run Monday–Sunday; the current week, month and year end today. `dailyAverage` is over the
  days that have a value (`daysWithData`): a day with nothing entered is unknown, not zero.
  `bestDay` is the highest-steps day (a tie goes to the earliest day); null when no day has
  more than zero steps. Unknown period → 422.
- `POST /api/activity/entries {date, steps?, distanceKm?, floors?, activeEnergyKcal?, standingMinutes?}` (201)
  → that day's values. One manual value per metric per day; posting again **replaces** it.
  Bounds: steps 0–100,000; distance 0–200 km; floors 0–500; energy 0–10,000 kcal; standing
  0–1,440 min. Not a future day; at most 366 days back.
- `DELETE /api/activity/entries/{date}` clears that day's manual values (synced rows stay).
- Every row carries `source` (`MANUAL` today). When Apple Health / Health Connect sync is built
  it writes rows with its own source; for each day and metric the largest source wins, so typed
  and synced steps are not added together.
- **Heart rate is never in this response** (tested). It is stored in the same table and returned
  raw, to its owner only, by `GET /api/health/readings`.

**Screen must.**
1. Period picker with the four periods; empty period shows "Nothing entered for this week" and
   the one next step (enter today's activity), never zeros drawn as a flat line.
2. Best-day card shows only date and that day's steps/distance/floors. No "personal record",
   medals, confetti, or "beat last week".
3. Show `daysWithData` next to every average so a 2-day average isn't read as a weekly one.
4. No calories-burned framing or weight-loss language on active energy.

**Questions.** Whether to ship manual entry at all before a sync source exists, or only
show trends once sync lands. Whether water history belongs on this screen.

## 3. Weight & BMI (Tier 1)

**Approved by:** _(design reviewer + clinical lead + student-wellbeing / counselling adviser)_

**Tier.** 1 (clinical value). **No canvas brief exists**; needs a canvas design.

**Backend (ready).**
- `GET /api/body/measurements` → `{weight:{id, value, unit:"kg", recordedAt, source}|null, height:{…, unit:"cm"}|null, bmi:{value, unit:"kg/m²", band, bands, reference, weightRecordedAt, heightRecordedAt}|null, bmiUnavailable: "NEEDS_WEIGHT_AND_HEIGHT"|"VALUE_OUT_OF_RANGE"|null, entries:[{id, metric, value, unit, recordedAt, source}]}`.
- `POST /api/body/measurements {weightKg?: 20–350, heightCm?: 100–250, recordedAt?}` (201). At least one value. Entries are deleted with `DELETE /api/health/readings/{id}`.
- BMI is computed on read from the latest weight and latest height, half-up to one decimal, and
  never stored. `bands` are the WHO cut-offs for Asian populations (2004) as neutral labels only:
  `Below 18.5`, `18.5–22.9`, `23–24.9`, `25 and above`; `band` is the one the shown value falls in.
  `reference` reads "WHO cut-offs for Asian populations (2004). Shown for information only."
- BMI is **never** in any summary, home, widget, trends or notification payload (tested on every
  wellness, meds, home and readings endpoint and on queued notifications).
- No differences between entries, no goals, no targets: the API computes none.

**Screen must (disordered-eating safeguards).**
1. **Opt-in and hidden by default.** The section is off until the student turns it on; when on,
   values are hidden behind a tap ("Show my measurements") each visit.
2. No goals, target weights, "ideal" ranges, progress bars, arrows, deltas or charts of change
   over time. Entries are a plain list for editing and deleting.
3. Bands are shown as the four neutral labels with the student's band marked in the same colour
   as the rest; no red/amber/green, no category words (under/over/normal/healthy/obese).
4. Crisis and support reachable on the screen (`CrisisSupport`), plus a quiet link to talk to a
   campus counsellor or doctor. No copy that comments on the number.
5. Never in notifications, widgets, the lock screen, the home feed or share sheets.

**Questions.** Whether BMI should be shown at all or only weight/height (some campuses' wellbeing
teams advise against BMI for students). Who owns the counselling link per campus.

## 4. Pill doses today ("x of y doses today", Taken / undo)

**Approved by:** _(design reviewer + clinical lead)_

**Brief.** `Medications.md` (Tier 1) · icons `arrow-left`, `check`, 3D `pill-alt--p3` · `✓` → `check`.

**Backend (ready).** Builds on `/api/meds/schedule`, `/api/meds/plans`, `/api/meds/log-dose`.
- `GET /api/meds/today` → `{date, timezone, plans:[{planId, name, dosage, dosesPlanned, dosesTaken, nextSlot, undo:{doseId, undoUntil}|null}]}`.
  `dosesPlanned` comes only from the structured `timesPerDay` (1–6); plans whose frequency is free
  text ("twice daily", "as needed") return `null` — the screen shows "{n} taken today", not
  "x of y". `nextSlot` is the ordinal of the next dose (2 = second dose today) or null; no clock
  times are stored, so none is shown.
- `POST /api/meds/plans {name, dosage?, frequency?, timesPerDay?: 1–6}`; `PATCH /api/meds/plans/{id} {timesPerDay: 1–6 | null}`.
- `POST /api/meds/log-dose {medId}` → now also `{doseId, undoUntil, dosesTaken}`. Up to
  `timesPerDay` doses per local day (one a day when unset, as before); further logs return
  `already_logged: true`.
- `DELETE /api/meds/doses/{doseId}` → undo within 30 minutes of logging; 404 for anyone else's or
  an unknown dose; 409 after the window. Audited.

**Screen must.**
1. "x of y doses today" only when `dosesPlanned` is set; Taken button disabled once `nextSlot` is
   null; Undo shown while `undo` is present, with the time it expires.
2. Offer "set doses per day" for plans without `timesPerDay`; never infer it from the frequency text.
3. Notifications stay generic. Reminder copy outside the app is "You have a medicine reminder in
   Student Kare. Open the app for details." (`workflow_scheduler.REMINDER_MESSAGES`), with no
   medicine name; logging or undoing a dose queues nothing.
4. Existing `/meds/schedule` still returns `currentStreak` and adherence windows; the reviewer
   should decide whether a streak is shown at all (it reads as gamification of a clinical habit).

## 5. Home-screen and lock-screen widgets (+ walkthrough and Premium upsell)

**Approved by:** _(design reviewer + clinical lead + privacy/DPDP owner + payments owner)_

**Tier.** 1 for anything that could show a health value. **No brief** (`AyushWidget.md` is the
in-app chat widget, unrelated). Needs canvas designs for each widget size and the walkthrough.

**Native work required (not in this repo yet).** iOS WidgetKit extension and Android Jetpack
Glance app widgets, an App Group / shared storage for the widget's last snapshot, background
refresh, and an Expo config plugin for both. None exists; nothing here can be built in React
Native alone.

**Backend.** None built for widgets on purpose. A widget should read a **separate** endpoint
returning only what that widget may show (e.g. water `percent` and `consumedMl`, doses
`dosesTaken`/`dosesPlanned` without names), never the full screen payloads. Propose
`GET /api/widgets/snapshot` in a later ticket once the designs fix the fields.

**Rules.**
1. **Lock screen never shows a health value**: no water, steps, doses, medicine names, weight or
   BMI. At most "Open Student Kare". Weight/BMI and heart rate never appear in any widget.
2. Home-screen widgets default to hidden values ("Tap to view") until the student opts in per
   widget; medicine names never appear in any widget.
3. Widget walkthrough carousel: generic illustrations and placeholder text only, never the
   student's own data.
4. **Upsell copy must not use health data** ("Add more widgets with Premium", never "You drank
   less this week — go Premium"). It may not be shown on the weight/BMI, doses or crisis screens.
5. **Price conflict to resolve before design.** The ticket says Premium ₹199/month, but the only
   student plan in `backend/services/billing.py` is **Student Plus ₹99/month**. Prices must come
   from the billing plans endpoint, never be hard-coded in widget or walkthrough copy. Product
   must decide the plan name and price, and whether widgets are a paid feature at all (Rule L:
   payment confers no extra visibility of anyone's health data).

## What is not built yet (for every plan)

- No Apple Health / Health Connect sync. `POST /api/v1/movement/background-sync` exists but keeps
  an in-memory list seeded with a demo row and is not persisted; it should be replaced by a real
  sync writing `care_readings` with its own `source` before any "connected" state is shown.
- `GET /api/health/readings` returns at most 1,000 rows across all metrics; heavy water logging
  can push older vitals out of a 90-day view. Add a `metric` filter before VitalTrends is built.
